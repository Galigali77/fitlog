```
│  · fetch_openGym.py   拉取清洗动作数据 → JSON        │
│  · optimize_gifs.py   GIF 压缩 / 尺寸归一             │
│  · serve.py           本地静态服务器                  │
└─────────────────────────────────────────────────────┘
```

### 1.2 架构原则

1. **本地优先**：IndexedDB 是数据的唯一权威来源，应用离线可完整使用；
2. **静态分发**：无任何运行时服务器依赖，构建产物 `dist/` 是纯静态文件，任意静态托管可跑；
3. **数据可携带**：JSON 导出即完整备份，导入即恢复（需求 FR-DATA-02/03）；
4. **媒体与代码分离**：动作数据、GIF 按需加载，不阻塞首屏。

## 2. 技术栈选型

### 2.1 产品代码（浏览器端，语言：JavaScript）

| 层     | 选型                         | 版本基线     | 理由                                                   |
| ----- | -------------------------- | -------- | ---------------------------------------------------- |
| 框架    | React                      | 19.x     | 已在原型中使用；生态最大，组件化适合记录类 UI                             |
| 语言    | JavaScript（ES2022+）        | —        | 开发者首选语言、心智成本低；模块语法、可选链等现代特性经 Vite 全量支持             |
| 代码规范  | ESLint（含 react-hooks 规则）  | 9.x      | 无静态类型后，靠 lint 兜住低级错误（未定义变量、依赖数组遗漏、不可达代码）          |

| 图标    | lucide-react               | 最新       | 轻量、风格统一                                              |
| 本地数据库 | Dexie.js                   | 4.x      | IndexedDB 的 Promise 封装，支持版本迁移，本身对 TS 无强依赖            |
| 状态管理  | React Context + useReducer | 内置       | 应用规模小，不引入 Redux/Zustand 之外的复杂度；跨组件数据仅 4\~5 类实体       |
| 路由    | react-router               | 7.x      | 原型已在用；后续加设置页/详情页需要                                   |
| PWA   | vite-plugin-pwa（Workbox）   | 最新       | 一行配置生成 SW： precache 静态资源 + 离线降级                      |
| 可视化   | 手写 SVG（零依赖）                | —        | 热力图/曲线/肌肉图数据量小，D3/ECharts 属于过重依赖，手写 SVG 已验证可行（原型复盘页） |
| 测试    | Vitest + Testing Library   | 3.x      | 与 Vite 同生态；重点覆盖超负荷引擎等纯函数逻辑                           |

#### 2.1.1 不用 TypeScript 的代价与对策

放弃静态类型是真实的取舍，本项目用四道防线弥补：

1. **JSDoc `@typedef` 定义数据模型**：在 `src/types/index.js` 用 `@typedef` 声明 Exercise / Workout / Set / Routine / BodyPhoto 等结构，编辑器（VS Code）照样给出字段补全和悬停提示，但不参与编译；
2. **ESLint 严格规则集**：`no-undef`、`no-unused-vars`、react-hooks 三条核心规则（exhaustive-deps）防住最常见错误；
3. **domain/ 纯函数 + Vitest**：业务逻辑（超负荷引擎、PR 检测、容量计算）保持无 UI 依赖的纯函数并写满测试——这是比类型更强的正确性保障；
4. **Repository 层收敛数据形状**：所有 IndexedDB 读写经 Repository，字段拼装在少数几个函数里完成，写错字段名只需在一层内排查。

> 判定：本项目实体少（8 张表）、页面少（6 个）、单人开发，TS 的收益有限、成本（类型体操、构建变慢、报错门槛）明显，JS + 上述防线是合理选择。若未来协作开发或实体关系复杂化，再迁移 TS 也不迟（Vite 支持渐进迁移）。

### 2.2 Python 工具链（开发机本地，语言：Python 3.11+）

| 脚本                          | 用途                                                                | 关键库                           |
| --------------------------- | ----------------------------------------------------------------- | ----------------------------- |
| `tools/fetch_openGym.py`    | 克隆/读取 openGym 仓库，清洗 `catalogue/` 动作数据为前端 JSON（字段映射、简体覆盖检查、缺失名单报告） | requests / gitpython / pandas |
| `tools/optimize_gifs.py`    | GIF 动图压缩、统一尺寸、生成缩略帧静态图（列表页用静帧、详情页才播 GIF，省流量）                      | Pillow                        |

### 3.1 结构决策理由

| 决策 | 理由 |
| --- | --- |
| 前端放 `app/` 子目录而非仓库根 | 仓库根留给 README/LICENSE/docs/tools，职责一眼分清；构建文件集中在 `app/` 内不污染根目录 |

### 3.3 Git 工作流（轻量版）

- **分支**：`main` 为唯一长期分支，要求随时可构建；每个阶段开短生命周期分支 `feat/phase1-data-layer`，完成即合回并删除——单人项目不搞复杂 GitFlow；
- **提交规范**：Conventional Commits，如 `feat: IndexedDB 数据层`、`fix: 计时器后台读秒`、`docs: 需求 v1.2`；
- **版本打 tag**：里程碑 M1~M5 各打一个 tag（`m1`、`m2`…），随时可回滚；
- **Issues 映射需求**：FR-XXX 每条需求建一个 Issue，里程碑对应 M1~M5，进度在 GitHub 可视；
- **CI（可选但推荐）**：GitHub Actions 在 push 时执行 `npm ci && npm run build && npm test`，防止 broken code 进 main。

## 4. 数据设计

### 4.1 IndexedDB 表结构（Dexie v1）

| 表                | 字段（主键 \*）                                                           | 索引                | 说明               |
| ---------------- | ------------------------------------------------------------------- | ----------------- | ---------------- |
| workouts         | \*id, date, title, routineId?, durationMin?, note?                  | date              | 一次训练             |
| workoutExercises | \*id, workoutId→workouts, exerciseId, order                         | workoutId         | 训练内的动作           |
| sets             | \*id, workoutExerciseId→workoutExercises, weight, reps, rpe?, type? | workoutExerciseId | 最小记录单元           |
| routines         | \*id, name, mode, rotationPos                                       | —                 | 计划               |
| routineItems     | \*id, routineId→routines, exerciseId, targetSets, targetReps        | routineId         | 计划内动作            |
| bodyPhotos       | \*id, date, front(blob), back(blob)                                 | date              | 身材记录（15 天/组）     |
| customExercises  | \*id, nameZh, muscles, equipment, desc                              | —                 | 用户自建动作（FR-EX-06） |
| settings         | \*key, value                                                        | —                 | 计时器默认值等单位设置      |

设计要点：

* **关系靠字段而非 join 库**：Workout → WorkoutExercise → Set 三级 1:N 用 workoutId/workoutExerciseId 字段表达，查询时组装；

* **版本迁移**：Dexie `version(1).stores({...})`，以后加字段走 `version(2).upgrade()`，对应需求"数据模型版本化"；

* **照片存 Blob 而非 dataURL**：Blob 更省空间、可直接 `<img src=blobURL>` 显示；

* **动作库只读**：内置动作来自 `public/exercises/index.json`，不进 IndexedDB；用户自建动作进 customExercises，查询时二者合并。

### 4.2 导出 JSON 格式（FR-DATA-02）

```json
{
  "app": "fitlog",
  "exportVersion": 1,
  "exportedAt": "2026-10-22T13:00:00+08:00",
  "data": { "workouts": [...], "routines": [...], "bodyPhotos": ["<base64>", ...], "settings": {...} }
}
```

导入时校验 `app` 与 `exportVersion` 字段，版本不兼容给出明确提示。

### 4.3 数据流转

```
用户操作 → Repository(写 IndexedDB) → Store 刷新 → UI
首次启动：种子数据（空计划 + 内置 4 模板）写入
页面读取：useLiveQuery 订阅 Dexie 表，数据变更自动重渲染
```

## 5. 关键模块设计

### 5.1 渐进超负荷建议引擎（domain/overload.js）

纯函数，输入历史组数据，输出建议列表，便于单测：

```python
# 算法伪代码（实际以 JavaScript 实现，逻辑相同）
def suggest(exercise_id, history_sets, routine_item, increment=2.5, cap_hits=2):
    recent = last_sessions(history_sets, n=cap_hits)          # 最近 N 次训练该动作
    if len(recent) < cap_hits: return None
    target_top = parse_top(routine_item.targetReps)            # 次数上限，如 "8-10" → 10
    if all(top_set(r).reps >= target_top for r in recent):     # 连续 N 次达上限
        return Suggest(加, current_weight + increment, reason="连续 N 次达到次数上限")
    if all(top_set(r).reps <= parse_bottom(routine_item.targetReps) for r in recent):
        return Suggest(减, current_weight - increment, reason="连续未达次数下限，触发减重")
    return None
```

配套规则（需求 FR-PLAN-07）：加重幅度、判定次数均可配置，存 settings。

### 5.2 PR 检测（domain/pr.js）

每完成一组：该组 `weight × reps` 与该动作**历史所有组**比较，超过即触发提示；同一次训练内同一动作只提示一次（原型已有，迁移为纯函数）。

### 5.3 组间计时器（hooks/useRestTimer.js）

* 状态机：idle → running(90s 可配) → done；

* 用 `setInterval` + `Date.now()` 差值计算（而非计数递减），**页面切后台被挂起后回前台读秒仍准确**（对应需求 5.3）；

* 结束时 `navigator.vibrate(200)` 震动 + 页面闪一下（降级：仅声音/视觉）。

### 5.4 PWA 方案（vite-plugin-pwa）

* **precache**：应用壳（HTML/JS/CSS）；

* **runtime cache**：动作库 JSON 与 GIF 采用 CacheFirst + 容量上限（如 GIF 最多缓存 200MB，LRU 淘汰）；

* 更新策略：新版本提示"刷新更新"（prompt 模式），避免训练中途强刷。

### 5.5 动作库按需加载

* 列表页：卡片显示 GIF 的**静态首帧**（Python 工具预生成 `thumbs/*.jpg`）；

* 仅当卡片进入视口（IntersectionObserver）才预载对应 GIF；

* 详情页大图 GIF 进入时才开始播放——3000+ GIF 全量加载体积不可接受，这是必须做的优化。

## 6. 技术路线图

> 对应需求分析第 11 章版本规划，展开为可执行路线。

### 阶段 1：数据层（目标：刷新不丢数据）

1. 引入 Dexie，建 8 张表（schema.js）+ Repository 层；
2. Store 全面改为 `useLiveQuery` 订阅 IndexedDB；
3. 身材照片改存 Blob；
4. 设置项持久化（计时器默认秒数、加重幅度）。

**验收**：完成一次训练 → 刷新页面 → 数据仍在；上传身材照片 → 刷新 → 仍在。

### 阶段 2：真实动作库（Python 工具首次登场）

1. 编写 `tools/fetch_openGym.py`：拉取 catalogue → 生成 `index.json`；输出简体中文覆盖率报告；
2. 编写 `tools/optimize_gifs.py`：压缩 + 生成首帧缩略图；
3. 前端动作库页改为读 `index.json` + 缩略图/GIF 懒加载；
4. 中文缺失条目补翻（人工或脚本+校对）。

**验收**：动作数 ≥3000；列表首屏只加载可见卡片的首帧；详情页 GIF 正常播放。

### 阶段 3：功能补全（P0 清零）

1. 计划编辑器（新建/复制模板/编辑动作与组数）；
2. 历史训练编辑与补记（改日期、改组数据，统计自动重算）；
3. 超负荷引擎接入真实数据（替换演示数据）；
4. 导出 JSON / CSV / 分享卡片 PNG；导入恢复；
5. PWA 接入 + 安装引导；
6. 计时器后台保活加固。

**验收**：需求文档第 10 章 5 条验收标准逐条通过。

### 阶段 4：测试与打磨

1. Vitest 覆盖 domain/ 纯函数（引擎、PR、容量计算）；
2. 真机走查：iOS Safari、Android Chrome 核心流程；
3. 性能核对：首屏 ≤3s（4G）、动作搜索 ≤200ms、逐组操作反馈 ≤100ms；
4. 边界：空数据态、365 天大数据量、浏览器存储接近上限提示。

### 阶段 5：发布自用

1. `npm run build` → `dist/`；
2. 部署到家用电脑/私有环境（`tools/serve.py` 或 nginx）；
3. 手机「添加到主屏幕」图文引导页；
4. 建立导出备份习惯（训练后温和提醒）。

## 7. 非功能需求实现方案

| 需求（文档第 6 章） | 实现手段                                            |
| ----------- | ----------------------------------------------- |
| 首屏 ≤3s      | 路由级代码分割；动作库 JSON 异步加载；GIF 零首屏依赖                 |
| 搜索 ≤200ms   | 前端内存索引（构建一次倒排），3000 条规模无需后端                     |
| 断网可用        | PWA precache + runtime cache（5.4）               |
| 不丢数据        | 组记录写完即提交事务；`beforeunload` 兜底；IDB 写失败立即提示并保留内存副本 |
| 隐私          | 无网络请求（除加载静态资源本身）；照片不出设备；导出由用户主动触发               |
| 存储上限        | 监听 `navigator.storage.estimate()`，超过 80% 提示导出清理 |
